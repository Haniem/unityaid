После генерации DOCX можно экспортировать PDF через Microsoft Word COM:

```powershell
$docx=(Resolve-Path -LiteralPath "docs\Документ диплома\generated\Zozin_UnityAid_VKR_final.docx").Path
$pdf=(Resolve-Path -LiteralPath "docs\Документ диплома\generated").Path + "\Zozin_UnityAid_VKR_final.pdf"
$word=New-Object -ComObject Word.Application
$word.Visible=$false
$doc=$word.Documents.Open($docx)
$doc.SaveAs([ref]$pdf,[ref]17)
$doc.Close($false)
$word.Quit()
```

## Что важно помнить по оформлению

Главный ориентир по оформлению: примеры в папке `Примеры`, особенно работа Афонькина для стиля описания предметной области и сравнения аналогов.

СМК лежит в папке `СМК`; оформление нужно сверять с ним и с готовыми студенческими примерами.

Не использовать видимые AI-метки, формулировки вроде «как ИИ», «сгенерировано» и прочее. Текст должен выглядеть как обычная дипломная работа студента.

Первые три страницы не генерировать автоматически, Павел планирует вставить их сам.

Следить, чтобы заголовки не были синими. В примерах заголовки черные, академические, без визуальной декоративности.

Названия подразделов не должны быть слишком короткими. Павел сравнивал с примером Афонькина: вместо короткого «Анализ аналогов» нужны развернутые академические названия, описывающие содержание раздела.

## Что еще можно улучшить

Сверить весь документ с СМК постранично: поля, интервалы, шрифты, оформление таблиц, рисунков, подписей, ссылок на рисунки и таблицы, список литературы, приложения.

Довести стиль всех подразделов до уровня раздела 1.2: меньше перечислений, больше связной аналитики, особенно в главах 2 и 3.

Проверить, что в тексте есть ссылки на все рисунки и таблицы перед их появлением. В академических работах лучше писать «На рисунке 5 представлена...», «В таблице 4 приведены...».

Проверить нумерацию рисунков, таблиц и приложений после всех правок. Если добавляются новые изображения, генератор может потребовать ручного обновления подписей и ссылок.

Расширить описание реализации, если преподаватель ожидает больше технической глубины: архитектура backend, структура API, модель данных, миграции, авторизация, роли, frontend-компоненты, сценарии работы.

Проверить приложения с кодом: они должны быть достаточно объемными, но не превращаться в бессистемную выгрузку файлов. Лучше выбирать фрагменты, которые демонстрируют ключевую логику: авторизация, заявки, учет времени, аналитика, сертификаты, админ-панель.

Проверить скриншоты приложения: они должны выглядеть наполненными и убедительными. Если в базе мало данных, перед финальным снятием скриншотов стоит заполнить демо-данные.

Проверить экономическую часть, если она требуется в финальном варианте. В папке есть материалы по экономике разработки web-приложений, но их нужно аккуратно связать с темой UnityAid.

Проверить список литературы: источники должны соответствовать фактическим ссылкам в тексте, быть оформлены по требованиям и включать реальные web-источники для Добро.рф, Idealist / VolunteerMatch, Timecounts, Golden.

Отдельно проверить приложения с API: таблица API уже исправлялась из-за выезда за границы страницы, но при добавлении новых endpoint может снова потребоваться сжатие, переносы или изменение ширины колонок.
