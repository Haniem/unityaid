# Реализованный функционал UnityAid

Документ фиксирует фактически реализованные модули системы на текущем этапе разработки и описывает, как пользователи разных ролей взаимодействуют с этими модулями.

## Роли и уровни доступа

### Неавторизованный пользователь

- Может открыть страницу входа.
- Может зарегистрироваться.
- Может подтвердить email через токен.
- Может запросить сброс пароля и установить новый пароль через токен.
- Не имеет доступа к основным разделам приложения без авторизации.

### Волонтер

- Работает в рамках организаций, в которых состоит.
- Видит доступные мероприятия, задачи, новости, базу знаний, свои часы, достижения и уведомления.
- Может подавать заявки на мероприятия.
- Может отменять собственную заявку на мероприятие.
- Может видеть статус своей заявки.
- Может отправлять отзыв после завершения мероприятия.
- Может вносить свои часы участия.
- Может смотреть свои достижения и место в рейтинге.
- Может редактировать собственный профиль.

### Координатор

- Управляет контентом в организациях, где имеет роль координатора.
- Может создавать и редактировать мероприятия, задачи, новости, статьи базы знаний в доступных организациях.
- Может рассматривать заявки на мероприятия.
- Может отмечать посещаемость и часы участников.
- Может завершать мероприятия и запускать начисление часов.
- Может назначать задачи волонтерам.
- Может просматривать обратную связь по мероприятиям своей организации.
- Может видеть управленческие отчеты по доступному контенту.

### Администратор организации

- Имеет возможности координатора.
- Может управлять организацией и ее участниками.
- Может назначать роли внутри организации.
- Может управлять логотипом и данными организации.
- Может администрировать волонтеров внутри своей организации.

### Суперадминистратор / системный администратор

- Имеет полный доступ к организациям и контенту.
- Может создавать и редактировать организации.
- Может управлять пользователями.
- Может назначать системные роли.
- Может видеть отчеты по всей системе.
- Может просматривать аудит действий пользователей.
- Может управлять системными справочниками, навыками и категориями.

## 1. Авторизация и учетные записи

### Реализовано

- Регистрация пользователя.
- Вход по email и паролю.
- JWT access token и refresh token.
- Обновление сессии через refresh token.
- Выход из аккаунта.
- Получение текущего пользователя.
- Смена пароля авторизованным пользователем.
- Запрос сброса пароля.
- Сброс пароля по токену.
- Подтверждение email.
- Хранение профиля пользователя на фронтенде.
- Автоматическая проверка сессии при переходе по защищенным маршрутам.

### Кейсы

1. Новый пользователь регистрируется, получает токен подтверждения и подтверждает email.
2. Волонтер входит в систему и попадает в рабочее пространство.
3. Пользователь с истекшим access token продолжает работу, если refresh token валиден.
4. Пользователь меняет пароль в настройках профиля.
5. Пользователь выходит из аккаунта, локальная сессия очищается.

## 2. Пользователи, волонтеры и роли

### Реализовано

- Список пользователей.
- Просмотр карточки пользователя.
- Редактирование пользователя.
- Список волонтеров.
- Просмотр профиля волонтера.
- Редактирование профиля волонтера.
- Статусы волонтера: `new`, `active`, `unavailable`, `archived`.
- Интересы, город, телефон, bio и расширенные данные профиля.
- Навыки волонтера.
- Создание и удаление навыков.
- Системные роли: `system_admin`, `system_manager`, `support`, `user`.
- Назначение системных ролей пользователю.
- Удаление системной роли у пользователя.
- Организационные роли: `super_admin`, `org_admin`, `coordinator`, `volunteer`.

### Кейсы

1. Волонтер обновляет свой профиль, добавляет город, телефон, интересы и навыки.
2. Координатор открывает список волонтеров своей организации и редактирует профиль волонтера.
3. Администратор организации назначает пользователя в организацию и задает роль.
4. Системный администратор назначает пользователю системную роль.
5. Системный администратор архивирует или активирует волонтера через профиль.

## 3. Организации

### Реализовано

- Список организаций.
- Создание организации.
- Просмотр организации.
- Редактирование организации.
- Удаление организации.
- Загрузка логотипа организации.
- Список участников организации.
- Добавление участника в организацию.
- Изменение роли участника.
- Удаление участника из организации.

### Кейсы

1. Системный администратор создает новую организацию.
2. Администратор организации обновляет описание, контакты и логотип.
3. Администратор организации добавляет волонтера в организацию.
4. Администратор организации повышает участника до координатора.
5. Координатор видит данные организации, но управление участниками зависит от прав.

## 4. Мероприятия и заявки

### Реализовано

- Список мероприятий.
- Создание мероприятия.
- Просмотр детальной страницы мероприятия.
- Редактирование мероприятия.
- Удаление мероприятия.
- Форматы: `online`, `offline`, `hybrid`.
- Статусы: `draft`, `published`, `completed`, `cancelled`.
- Даты начала и окончания.
- Локация.
- Лимит участников.
- Check-in код для отметки посещаемости.
- Подача заявки на мероприятие.
- Автоматическое определение статуса заявки с учетом лимита участников.
- Статусы заявки: `pending`, `approved`, `waitlisted`, `rejected`, `cancelled`.
- Просмотр заявок координатором.
- Изменение статуса заявки координатором.
- Отмена собственной заявки волонтером.
- Список подтвержденных участников.
- Смены мероприятия.
- Создание смены.
- Завершение мероприятия.

### Кейсы

1. Координатор создает мероприятие, указывает организацию, формат, время, место и лимит участников.
2. Волонтер открывает мероприятие и подает заявку с комментарием.
3. Координатор рассматривает заявки и подтверждает участника.
4. Если лимит заполнен, новая заявка может попасть в лист ожидания.
5. Волонтер видит статус своей заявки.
6. Волонтер отменяет свою заявку.
7. Координатор создает смены для мероприятия.
8. После проведения координатор завершает мероприятие, и система запускает начисление часов и геймификацию.

## 5. Посещаемость и учет часов

### Реализовано

- Отметка посещаемости участника на мероприятии.
- Учет часов по мероприятию.
- Редактирование часов посещения.
- Создание записей времени волонтером.
- Список записей времени.
- Редактирование своей записи времени.
- Подтверждение записи времени координатором.
- Отклонение записи времени координатором.
- Связь часов с организацией, мероприятием или задачей.
- Отдельная страница "Мои часы".

### Кейсы

1. Волонтер добавляет запись времени по мероприятию или задаче.
2. Координатор открывает список часов и проверяет записи.
3. Координатор подтверждает запись, после чего часы учитываются в профиле.
4. Координатор отклоняет запись, если данные некорректны.
5. Координатор отмечает посещаемость на странице мероприятия и корректирует часы.

## 6. Задачи

### Реализовано

- Список задач.
- Создание задачи.
- Просмотр задачи.
- Редактирование задачи.
- Удаление задачи.
- Связь задачи с организацией и опционально с мероприятием.
- Статусы задач: `created`, `assigned`, `in_progress`, `review`, `completed`, `cancelled`.
- Приоритеты: `low`, `medium`, `high`.
- Срок выполнения.
- Назначение исполнителей.
- Удаление назначения.
- Комментарии к задаче.
- Вложения к задаче.
- История статусов.
- Учет времени внутри задачи.
- Подтверждение выполнения задачи.
- Автоматический перерасчет геймификации после подтверждения задачи.

### Кейсы

1. Координатор создает задачу и назначает волонтера исполнителем.
2. Волонтер видит назначенную задачу и открывает ее карточку.
3. Участники обсуждают задачу в комментариях.
4. Волонтер добавляет вложение или запись времени по задаче.
5. Координатор меняет статус задачи.
6. Координатор подтверждает выполнение, задача становится завершенной, а волонтер получает прогресс в геймификации.

## 7. Новости

### Реализовано

- Список новостей.
- Создание новости.
- Просмотр новости.
- Редактирование новости.
- Удаление новости.
- Категории новостей.
- Создание категории.
- Статусы: `draft`, `published`, `scheduled`.
- Запланированная публикация.
- Автоматическая публикация запланированных новостей при загрузке списка.
- Обложка новости.
- Загрузка изображений для новостей.
- Очистка неиспользуемых файлов.
- Поиск и фильтры.
- Защита длинного текста от выхода за границы экрана.

### Кейсы

1. Координатор создает новость для своей организации.
2. Координатор добавляет обложку и HTML-содержимое.
3. Координатор сохраняет новость как черновик.
4. Координатор планирует публикацию на будущую дату.
5. Волонтер открывает опубликованную новость и читает материал.
6. Администратор очищает неиспользуемые файлы новостей.

## 8. Геймификация

### Реализовано

- Таблица достижений.
- Правила достижений.
- Достижения пользователя.
- Транзакции начисления баллов.
- Профиль геймификации пользователя.
- Лидерборд.
- Уровень волонтера.
- Прогресс до следующего уровня.
- Перерасчет достижений.
- Автоматические достижения:
  - регистрация;
  - заполненный профиль;
  - первое участие;
  - выполненная задача;
  - 10 часов помощи;
  - 25 часов помощи;
  - 50 часов помощи;
  - 100 часов помощи.

### Кейсы

1. Волонтер регистрируется и получает первое достижение.
2. Волонтер заполняет профиль и получает баллы за заполнение.
3. После посещения мероприятия система учитывает участие.
4. После подтверждения задачи волонтер получает достижение за выполненную задачу.
5. Волонтер открывает страницу достижений и видит уровень, баллы, прогресс и лидерборд.
6. Координатор или администратор запускает перерасчет достижений.

## 9. Аналитика и отчеты

### Реализовано

- Отдельная страница "Аналитика" как каталог отчетов.
- Отчет "Обзор".
- Отчет "Волонтеры".
- Отчет "Мероприятия".
- Отчет "Задачи".
- Отчет "Начисления".
- Отчет "Действия сотрудников".
- Фильтр периода.
- Карточки ключевых метрик.
- Простые графики активности и распределений.
- Топ волонтеров.
- Таблица последних начислений геймификации.
- Таблица последних действий сотрудников.

### Кейсы

1. Администратор открывает каталог аналитики и выбирает нужный отчет.
2. Координатор смотрит отчет по мероприятиям: заявки, посещаемость, статусы.
3. Администратор смотрит отчет по волонтерам: активные, новые, уровни и часы.
4. Администратор смотрит отчет по задачам: статусы, приоритеты, выполненные задачи.
5. Администратор анализирует начисления: кому, сколько и за что начислены баллы.
6. Системный администратор открывает отчет по действиям сотрудников и проверяет активность.

## 10. Аудит действий пользователей

### Реализовано

- Таблица `audit_log`.
- Middleware для автоматической записи изменяющих запросов.
- Записываются `POST`, `PUT`, `PATCH`, `DELETE` защищенных API.
- Фиксируются пользователь, метод, действие, раздел системы, объект, путь, HTTP-статус, IP, user-agent и время.
- Отчет в аналитике по действиям сотрудников.

### Кейсы

1. Координатор создает задачу, действие попадает в аудит.
2. Администратор редактирует организацию, действие попадает в аудит.
3. Системный администратор меняет роли пользователя, действие попадает в аудит.
4. Системный администратор открывает отчет "Действия сотрудников" и видит последние операции.
5. Администратор фильтрует отчет по периоду и анализирует ошибки или удаления.

## 11. Уведомления

### Реализовано

- Таблица уведомлений.
- Список уведомлений пользователя.
- Счетчик непрочитанных в topbar.
- Выпадающее меню уведомлений.
- Страница всех уведомлений.
- Отметка одного уведомления прочитанным.
- Отметка всех уведомлений прочитанными.
- Переход из уведомления в связанный раздел.
- Уведомления о подтверждении заявки.
- Уведомления об отклонении заявки.
- Уведомления о назначении задачи.
- Уведомления об изменении задачи.
- Уведомления о полученном достижении.
- Напоминания о мероприятиях, которые начнутся в ближайшие 24 часа.

### Кейсы

1. Координатор подтверждает заявку, волонтер получает уведомление.
2. Координатор отклоняет заявку, волонтер получает уведомление.
3. Координатор назначает задачу, исполнитель получает уведомление.
4. Координатор изменяет задачу, назначенные участники получают уведомления.
5. Волонтер получает достижение и видит уведомление.
6. Волонтер открывает меню уведомлений и переходит к связанному мероприятию или задаче.
7. Пользователь отмечает уведомления прочитанными.

## 13. Обратная связь по мероприятиям

### Реализовано

- Форма обратной связи на странице мероприятия.
- Оценка по шкале 1-5.
- Комментарий к отзыву.
- Сохранение и обновление собственного отзыва пользователя.
- Просмотр всех отзывов координатором.
- Средняя оценка мероприятия.
- Количество отзывов.
- Ограничение видимости: координатор видит все отзывы, обычный пользователь видит только свой отзыв.
- Форма отзыва открывается после завершения мероприятия.

### Кейсы

1. Координатор завершает мероприятие.
2. Волонтер открывает завершенное мероприятие и оставляет оценку со звездочками.
3. Волонтер добавляет комментарий к отзыву.
4. Волонтер повторно отправляет форму, и его отзыв обновляется.
5. Координатор открывает мероприятие и видит все отзывы участников.
6. Координатор смотрит среднюю оценку мероприятия и количество отзывов.

### Реализовано

- Backend-описания форм для создания и редактирования сущностей.
- Формы для организаций, мероприятий, задач и новостей.
- Проверка прав доступа при запросе формы.
- Возможные значения для селектов.
- Метаданные полей: тип, label, required, help, options.

### Кейсы

1. Frontend запрашивает схему формы создания мероприятия.
2. Backend возвращает поля, доступные текущему пользователю.
3. Пользователь заполняет форму, а frontend может построить интерфейс по схеме.

## 17. Текущие ограничения и зоны развития

- Экспорт отчетов пока не реализован.
- Расширенные визуализации аналитики пока не реализованы.
- В аудите пока фиксируется факт действия, но не детальный diff измененных полей.
- Уведомления реализованы как in-app уведомления без email/push рассылки.
- База знаний использует HTML-содержимое с базовой sanitization.
- Сертификаты и справки еще не реализованы.
- Полный security hardening из дальнейшего этапа еще впереди.
- Swagger/OpenAPI и итоговая документация API еще не реализованы.

## 18. Сертификаты и справки

### Реализовано

- Таблица `certificates`.
- Генерация справок о волонтерских часах.
- Генерация сертификатов участия.
- Расчет суммы подтвержденных часов по волонтеру и организации.
- Уникальный проверочный код документа.
- Скачивание PDF.
- Публичная проверка сертификата по коду.
- Страница `/certificates`.
- Страница `/certificates/verify/{code}`.
- Пункт "Сертификаты" в основном меню.

### Кейсы

1. Координатор выбирает волонтера, тип документа и организацию, затем формирует справку о часах.
2. Волонтер открывает список своих сертификатов и скачивает PDF.
3. Внешний проверяющий вводит код на публичной странице и видит подтверждение документа.
4. Администратор просматривает все сертификаты через системную админ-панель.

## 19. Системная админ-панель

### Реализовано

- Страница `/admin`.
- Переход из настроек для супер-администратора.
- Whitelist доступных сущностей.
- Постраничный просмотр записей.
- Поиск по разрешенным полям.
- Создание, редактирование и удаление разрешенных записей.
- Управление пользователями, организациями, участниками, мероприятиями, задачами, часами, новостями, базой знаний, сертификатами и справочными таблицами.
- Просмотр audit log без возможности ручного изменения.
- Доступ только для роли `super_admin`.

### Кейсы

1. Супер-администратор открывает настройки и переходит в системную админ-панель.
2. Супер-администратор выбирает сущность `users`, создает пользователя или редактирует его данные через JSON-форму.
3. Супер-администратор фильтрует записи по поиску и переходит по страницам.
4. Супер-администратор удаляет тестовую сущность там, где удаление разрешено.
5. Супер-администратор открывает `audit_log` и проверяет последние изменяющие действия пользователей.

## 20. Безопасность и документация

### Реализовано

- Rate limit для auth endpoint.
- Проверка MIME-типа загружаемых изображений.
- Sanitization HTML для WYSIWYG-контента.
- Audit middleware для изменяющих запросов.
- Отчет по действиям сотрудников.
- Документы `docs/codex/api_overview.md`, `docs/readme/launch_instructions.md`, `docs/readme/user_guide.md`, `docs/readme/admin_guide.md`, `docs/codex/er_diagram.md`, `docs/codex/testing_checklist.md`.

### Кейсы

1. Пользователь с множеством попыток входа получает временное ограничение.
2. Администратор загружает только валидное изображение для новости или логотипа.
3. Системный администратор проверяет действия сотрудников в аналитике и в админ-панели.
4. Команда запускает проект по инструкции и проходит приемочный чеклист.
