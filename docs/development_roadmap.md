### 4.2. Системные роли и роли в организации

Статус: **готово**

В системе нужно разделить два уровня прав:

1. **Системная роль** - определяет, что пользователь может делать во всем приложении.
2. **Роль в организации** - определяет, что пользователь может делать внутри конкретной организации.

Системная роль должна храниться отдельно от членства в организации. Рекомендуемая модель:

- таблица `users` хранит базовый профиль пользователя;
- таблица `system_roles` хранит справочник системных ролей;
- таблица `user_system_roles` связывает пользователя с одной или несколькими системными ролями;
- таблица `organization_members` остается таблицей ролей внутри организации.

Базовые системные роли:

- `system_admin` - полный доступ ко всей системе, настройкам, пользователям, организациям, справочникам и аудиту;
- `system_manager` - управление пользователями, справочниками и проверка данных без критичных системных настроек;
- `support` - просмотр данных и помощь пользователям без права менять роли и удалять данные;
- `user` - обычный пользователь системы, права которого дальше определяются членством в организациях.

Базовые роли внутри организации:

- `org_admin` - управляет своей организацией, участниками, ролями, мероприятиями, задачами и новостями организации;
- `coordinator` - управляет мероприятиями, заявками, задачами и волонтерами своей организации;
- `volunteer` - редактирует свой профиль, подает заявки, выполняет задачи и фиксирует вклад.

Правила работы ролей:

- системные роли назначает только пользователь с ролью `system_admin`;
- организационные роли назначает `system_admin` или `org_admin` соответствующей организации;
- системная роль не заменяет организационную: например, `support` может видеть данные для поддержки, но не становится координатором организации;
- при проверке прав backend сначала проверяет системные права, затем права в конкретной организации;
- аудит назначения системных и организационных ролей реализуется в этапе 10 "Безопасность и аудит";
- пользователь может состоять в нескольких организациях и иметь разные организационные роли в каждой из них.

Основные endpoint для системных ролей:

```http
GET /api/v1/system-roles
GET /api/v1/users/{id}/system-roles
PUT /api/v1/users/{id}/system-roles
DELETE /api/v1/users/{id}/system-roles/{roleId}
```

## 17. Definition of Done для MVP

MVP считается готовым, если:

- система запускается через Docker одной командой;
- есть демо-данные;
- пользователь может войти;
- роли пользователей различаются;
- волонтер может заполнить профиль;
- координатор может создать мероприятие;
- волонтер может подать заявку;
- координатор может подтвердить заявку;
- участие можно отметить;
- волонтерские часы учитываются;
- задача может быть создана и выполнена;
- за подтвержденные действия начисляются баллы;
- администратор видит базовую аналитику;
- основные страницы не содержат заглушек;
- API задокументировано;
- критичные сценарии проверены.
