# Сравнение ВКР Афонькина М.А. с ВКР Зозина П.А. и план версии V4 «Пульс»

## 1. Назначение анализа

Цель анализа - определить, какие элементы подачи, структуры и доказательной базы хорошо реализованы в работе Афонькина М.А. и должны быть перенесены в следующую редакцию ВКР по системе «Пульс», не копируя чужой текст и не заявляя непроверенную функциональность.

Сравнивались документы:

- образец: `Примеры/Afonkin_M_A_VKR_2 (1).docx`;
- текущая версия: `Zozin_Puls_VKR_final_V3_dorabotannaya.docx`.

Метод проверки:

- извлечение структуры DOCX: заголовков, подписей таблиц и рисунков, приложений, текста и признаков служебной разметки;
- рендер обеих работ через LibreOffice в PDF и визуальный просмотр страниц;
- сопоставление структуры глав, роли рисунков и таблиц, состава доказательств, приложений и оформления списка источников;
- проверка рекомендаций на реализуемость для реального репозитория «Пульс».

Важно: работа Афонькина используется как ориентир по композиции и доказательности, но не заменяет требования пособия СМК и не может служить основанием для переноса чужих формулировок или неподтвержденных результатов.

## 2. Итоговый вывод

V3 по количеству моделей и обязательных результатов уже шире работы Афонькина: в ней присутствуют структура предметной области, IDEF0, модель информационных потоков, концептуальная модель, архитектура, логическая и физическая модели БД, несколько блок-схем, карта экранов, макеты форм, аналитика, контент-план, программа испытаний и большой листинг реального кода.

Однако работа Афонькина воспринимается сильнее в трех аспектах:

1. Она показывает реализованный продукт непосредственно в основной части текста: экранные снимки встроены рядом с описанием функций, пользовательского и административного сценариев.
2. Она подробно раскрывает реализацию на уровне инженерных артефактов: словарь физических таблиц, REST-маршруты, DevOps-раздел, этапы CI/CD и приложение с конфигурацией pipeline.
3. Она оформляет научный аппарат убедительнее: источники активно цитируются в тексте, а библиографический список приведен в едином полном формате.

Для V4 не требуется расширять объем ради объема. Требуется сделать ВКР «Пульс» более доказательной: сократить проектно-обещающий тон, добавить подтвержденные экраны сквозного сценария, раскрыть фактические структуры БД и развертывания, привести ссылки и начальные листы к уровню образца.

Для финального официального комплекта V4 потребуются:

Эти материалы нельзя корректно сгенерировать как состоявшиеся официальные документы.

## 6. Сравнение второй главы

### 6.1 Что особенно хорошо сделано у Афонькина

Вторая глава образца строит убедительную цепочку реализации:

1. Архитектура веб-приложения с объяснением технологического стека.
2. Функциональные требования и сценарии использования с таблицами и диаграммой вариантов использования.
3. Проектирование БД с логической схемой и детальными таблицами физических атрибутов.
4. Разбор предметно значимых алгоритмов: рейтинг и геймификация, сразу сопровождаемые экранами интерфейса.
5. Отдельные подразделы серверной части, клиентской части и административной панели.
6. Отдельный раздел DevOps и воспроизводимости развертывания с Docker Compose, CI/CD, таблицей этапов pipeline и схемой процесса.

### 6.2 Что уже присутствует в V3 и должно сохраниться

В V3 имеются:

- концептуальная модель программного обеспечения;
- архитектурная схема;
- схема функционирования от мероприятия к отчету;
- функциональные требования по ролям;
- структура данных, информационно-логическая и физическая модель БД;
- группы REST API;
- пять блок-схем ключевых алгоритмов;
- карта экранов;
- макеты пользовательских форм и визуализации результатов;
- контент-план;
- описание Docker Compose и сопровождения.

Эти элементы являются прямым закрытием требований пособия и не должны быть удалены при перестройке V4 под образец.

### 6.3 Что у Афонькина есть, а в V3 раскрыто слабее

#### A. Полный словарь физической модели данных

У Афонькина после логической модели идут таблицы со структурой конкретных сущностей: поле, тип данных, назначение. В V3 сейчас имеются укрупненные сущности и ограничения, но нет систематического словаря основных таблиц «Пульс».

Для V4 требуется добавить подраздел в `2.3 Проектирование базы данных`:

- таблица `users`;
- таблица `organizations`;
- таблица `organization_members`;
- таблица `events`;
- таблица заявок на мероприятие;
- таблица `tasks` и при необходимости назначений;
- таблица учета времени;
- таблицы достижений/баллов;
- таблица сертификатов;
- таблица аудита.

Для каждой сущности следует приводить только реально существующие в миграциях поля: имя поля, тип, ключ/ограничение, назначение. Если таблиц слишком много для основной части, основные таблицы оставить в главе 2, а полный словарь вынести в приложение А.

#### B. Явная диаграмма вариантов использования

У Афонькина в разделе функциональных требований есть диаграмма вариантов использования, связывающая роли и операции. V3 содержит функциональные модули, карту экранов и таблицу ролей, но отдельная UML use case diagram отсутствует.

Для V4 рекомендуется добавить рисунок после таблицы функциональных требований:

`Рисунок ... - Диаграмма вариантов использования информационной системы «Пульс»`.

Участники: волонтер, координатор, администратор организации, суперадминистратор, внешний проверяющий сертификата. Варианты использования должны соответствовать существующим API и страницам.

#### C. Показ реализации предметных модулей через реальный интерфейс

У Афонькина рейтинговая модель и геймификация сопровождаются реальными скриншотами результата в основной главе. В V3 модули аналитики, достижений и сертификатов описаны, но реальные экраны сосредоточены в приложении Д.

Для V4 в подраздел `2.6 Реализация модулей аналитики, геймификации и сертификатов` следует встроить:

- экран аналитической панели с показателями и пояснением, какие API-данные отображаются;
- экран достижений/рейтинга, если он фактически доступен и заполнен данными;
- экран сертификатов и публичной проверки сертификата;
- ссылки из текста на увеличенные варианты в приложении Д.

#### D. Административная панель как отдельный предмет разработки

У Афонькина административная панель выделена самостоятельным подразделом. У V3 системное администрирование упоминается как модуль и подтверждается одним снимком в приложении.

В V4 целесообразно выделить подраздел:

`2.7 Разработка административных функций и разграничение доступа`

В нем необходимо показать:

- какие операции доступны администратору организации;
- какие операции доступны суперадминистратору;
- как контекст организации ограничивает доступ;
- какой экран или API-ответ подтверждает каждую критическую операцию;
- связь с журналом аудита.

После вставки подраздела выводы второй главы следует перенумеровать.

#### E. Воспроизводимое развертывание и автоматическая проверка

У Афонькина имеется отдельный DevOps-раздел и приложение с листингом CI/CD pipeline. В V3 Docker Compose упоминается, но доказательная часть ограничена описанием и результатами двух команд сборки.

Фактически в репозитории «Пульс» присутствуют:

- корневой `docker-compose.yml`;
- Dockerfile для backend и frontend;
- production Dockerfile;
- compose-конфигурации в `deploy/client` и `deploy/control-plane`;
- healthcheck-конфигурации и PowerShell-скрипты запуска, обновления, резервного копирования и восстановления.

При этом отдельного workflow GitHub Actions в текущем репозитории не обнаружено. Поэтому V4 не должна утверждать наличие CI/CD pipeline, пока такой workflow действительно не будет создан и проверен.

Для V4 принято решение реализовать второй вариант: создать реальный workflow GitHub Actions для frontend, backend и контейнерной конфигурации, выполнить его проверку, а затем описать как реализованный результат. В раздел также должны войти фактические Docker Compose-конфигурации, healthcheck и процессы backup/restore.

Это отдельная программная доработка, а не текстовая вставка: в диплом можно включить CI/CD только после добавления workflow в репозиторий и получения подтвержденного результата его выполнения.

## 7. Сравнение третьей главы и доказательств работоспособности

### 7.1 Сильная композиция Афонькина

Глава 3 образца содержит:

- подготовку демонстрационных данных;
- пользовательский сценарий с таблицами шагов и снимками конечных экранов;
- административный сценарий с таблицами и снимками результата действия;
- проверку качества интерфейса;
- проверку сборки и развертывания;
- анализ результатов и ограничений;
- выводы.

Особенно полезный прием образца: автор показывает не только форму действия, но и состояние после сохранения или модерации. Это превращает изображение интерфейса в доказательство сценария.

### 7.2 Текущее состояние V3

V3 обладает более развитой методикой проверки:

- разделяет результаты на подтвержденные запуском, подтвержденные кодом и требующие опытной проверки;
- содержит программу испытаний, приемочные критерии, негативные сценарии, аудит, метрики, журнал пилота и форму итогового протокола;
- честно указывает, что backend-тестов в репозитории нет, а `go test ./...` подтверждает компилируемость;
- подтверждает production-сборку frontend.

Это сильнее образца с точки зрения академической честности. Сохранять эту честность обязательно.

### 7.3 Главный разрыв V3

V3 содержит план и методику полного пилотного сценария, но не содержит заполненный фактический протокол прохождения сценария с данными, экранными снимками результатов и проверенными изменениями показателей.

У Афонькина текст подает сценарии как реально пройденные и снабжает их скриншотами. Чтобы V4 стала убедительнее образца без неподтвержденных заявлений, необходимо фактически выполнить демонстрационный цикл «Пульс» и задокументировать его.

### 7.4 Необходимый фактический сценарий для V4

Следует развернуть приложение на тестовых данных и пройти сценарий:

1. Вход администратора или создание тестовой организации.
2. Создание/проверка участников с ролями волонтера и координатора.
3. Публикация мероприятия.
4. Подача заявки волонтером.
5. Подтверждение заявки координатором.
6. Создание задачи или отметка участия.
7. Внесение волонтерских часов.
8. Подтверждение часов координатором.
9. Проверка изменения аналитического показателя.
10. Проверка появления достижения/баллов, если соответствующее правило срабатывает на выбранных данных.
11. Формирование сертификата.
12. Публичная проверка сертификата по коду.
13. Проверка журнала аудита для критичных операций.

Для каждого этапа в V4 нужно указать:

- роль исполнителя;
- исходное состояние;
- выполненное действие;
- ожидаемый результат;
- фактический результат;
- доказательство: скриншот интерфейса, ответ API, запись журнала или лог команды.

### 7.5 Рисунки, которые следует добавить в основную часть главы 3

## 8. Источники и научный аппарат

### 8.1 Преимущество образца

В работе Афонькина библиографический список из 30 источников активно связан с текстом: в документе обнаружено около 31 внутритекстовой ссылки вида `[n]`. Источники оформлены в единообразном библиографическом формате с указанием электронного ресурса, URL, даты обращения и режима доступа, где это применимо.

### 8.2 Проблема V3

В V3 приведено 46 источников, но в основном тексте обнаружены только три внутритекстовые ссылки: `[7]`, `[8]`, `[9]`, относящиеся главным образом к актуальности темы. Это означает, что большая часть:

- теоретического анализа;
- архитектурного обоснования;
- проектирования БД;
- REST-подхода;
- пользовательского интерфейса;
- тестирования;
- Docker-развертывания

не связана с указанными источниками непосредственно в тексте.

Также часть источников V3 оформлена кратко, без полноты библиографического описания, которая видна в образце.

### 8.3 Исправления для V4

Требуется:

- расставить ссылки на источники во введении, главе 1, при обосновании архитектуры, БД, API, UX, безопасности, тестирования и развертывания;
- не ссылаться на источник, если он не использован в конкретном утверждении;
- привести источники к единому библиографическому оформлению по шаблону пособия;
- для электронных источников указывать URL и дату обращения;
- проверить допустимую долю электронных ресурсов согласно пособию;
- проектные документы «Пульс» оставить в списке только если они допустимы как источники и действительно используются в тексте как материалы разработки.

Приоритет: высокий. Формально длинный список литературы без ссылок в тексте выглядит слабее более короткого, но реально используемого списка Афонькина.

## 9. Оформление, визуальная подача и читаемость

### 9.1 Что следует перенять из образца

- Реальные скриншоты продукта в основной части, а не только в приложениях.
- Схема: объяснение функции -> ссылка на рисунок -> рисунок -> интерпретация результата.
- Табличное описание сценариев до показа их экранных результатов.
- Отдельное раскрытие инфраструктуры и воспроизводимости запуска.
- Детальное физическое описание данных.

### 9.2 Что не следует перенимать автоматически

- Чужой текст, формулировки предметной области и названия сущностей.
- Заявления об опытной эксплуатации или CI/CD без фактического подтверждения для «Пульс».
- Структурные особенности образца, если они конфликтуют с требованиями пособия. Например, V3 уже содержит обязательные модели, отсутствующие в образце; их удалять нельзя.

### 9.3 Унификация оформления V4

При подготовке V4 следует:

- заменить дефисы в подписях рисунков и таблиц на единый типографский разделитель согласно принятому шаблону;
- пересчитать статистику реферата после финальной верстки;
- обновить содержание после добавления новых подразделов;
- обеспечить ссылку из текста на каждый новый рисунок и таблицу;
- проверить, что подпись не отрывается от рисунка или таблицы;
- сохранить отсутствие выделений, комментариев и служебных пометок.

## 11.1 Новые функции продукта, принятые в объем V4

### 11.1.1 GitHub Actions и подтвержденная инженерная воспроизводимость

Цель доработки - реализовать для «Пульс» реальный автоматизированный контур проверки, аналогичный сильной инженерной части работы Афонькина, но построенный по фактическому стеку текущего проекта.

Текущее основание в проекте:

- frontend построен на Vue.js, TypeScript и Vite и уже успешно собирается командой `npm run build`;
- backend реализован на Go и компилируется через `go test ./...`, однако автоматизированные тестовые файлы пока отсутствуют;
- в проекте уже имеются Dockerfile, Docker Compose-конфигурации, healthcheck и эксплуатационные скрипты.

Необходимо реализовать в репозитории:

| Компонент workflow | Реализуемые шаги | Доказательство для ВКР |
| --- | --- | --- |
| Backend job | checkout, setup Go, загрузка зависимостей, `go vet ./...`, `go test ./...`, `go build ./...` | Лог успешной сборки; честное указание состава тестов |
| Frontend job | checkout, setup Node, `npm ci`, `npm run build` | Лог production-сборки |
| Container/config job | проверка Docker Compose-конфигурации, сборка контейнеров, запуск тестового контура, проверка healthcheck backend/frontend/db | Лог запуска и статусов сервисов |
| Artifact/summary | сохранение итогов проверки или краткого отчета job summary | Артефакт, включаемый в приложение диплома |

Правила достоверности:

- не заявлять автоматические тесты backend как выполненные, пока они действительно не добавлены;
- не заявлять успешный workflow до фактического запуска в GitHub Actions;
- после реализации включить в ВКР фрагмент YAML workflow, схему стадий CI/CD и таблицу фактически полученных результатов;
- связать CI/CD с Docker Compose, healthcheck и воспроизводимым демонстрационным контуром.

### 11.1.2 Обновленный профиль пользователя

Цель доработки - превратить текущую компактную страницу профиля в рабочую карточку волонтера, где отображаются его данные, участие, вклад и документы. В текущей реализации уже имеются `users.avatar_url`, `volunteer_profiles`, навыки, часы и данные геймификации; новая функция должна развить эту основу.

#### Обязательная структура вкладок

| Вкладка | Назначение | Пример состава |
| --- | --- | --- |
| `Личная информация` | Основные данные пользователя и настраиваемые поля персонального блока | ФИО, телефон, город, аватар, контакты, дополнительные поля организации |
| `Работа` | Опыт и организационный контекст волонтера | Организации, роль, описание опыта, навыки, интересы, статус доступности, пользовательские поля рабочих групп |
| `Задачи` | Назначенные пользователю задачи | Статус, приоритет, срок, связанное мероприятие, история выполнения |
| `Мероприятия` | Участие волонтера в событиях | Заявки, подтвержденное участие, часы, будущие и завершенные мероприятия |
| `Достижения и документы` | Подтвержденный вклад и результаты мотивации | Баллы, уровень, достижения, сертификаты и ссылка на публичную проверку |

Дополнительно для владельца профиля должен быть доступен сценарий изменения аватара и редактирования разрешенных полей, а для администратора - просмотр данных в рамках доступной организации.

#### Смена аватара

Сейчас поле `avatar_url` уже существует, но форма редактирования принимает URL. Для V4 требуется полноценный пользовательский сценарий:

- загрузка изображения через интерфейс профиля;
- preview перед сохранением;
- ограничения типа и размера файла;
- хранение URL загруженного файла в существующем поле `users.avatar_url`;
- обновление изображения в верхней панели и профиле после сохранения;
- обработка отсутствующего аватара через нейтральный fallback;
- проверка прав: пользователь меняет собственный аватар, администратор - только в предусмотренном политикой сценарии.

#### Отображение вкладок

- На широком экране использовать горизонтальные вкладки над содержанием профиля.
- На мобильном экране вкладки должны оставаться доступными без наложений: горизонтальная прокрутка или компактное меню разделов.
- В каждой вкладке показывать пустое состояние, если данных еще нет.
- Критичные данные, такие как подтвержденные часы и сертификаты, показывать как результат подтвержденных операций, а не как произвольные редактируемые значения.

### 11.1.3 Конструктор групп и пользовательских полей профиля

Цель функции - позволить администратору организации самостоятельно определять дополнительные данные, которые должны заполнять волонтеры, сохраняя системные поля и единое представление профиля.

#### Поведение административного интерфейса

По предоставленным примерам в административной части нужна страница `Поля профиля`:

- список групп полей с раскрытием/сворачиванием;
- системные группы и поля отображаются как дефолтные и не подлежат удалению;
- пользовательские группы можно добавлять, редактировать, упорядочивать и отключать;
- пользовательские поля можно добавлять в группу, редактировать, копировать, активировать/деактивировать и упорядочивать;
- форма создания/редактирования поля содержит название, код, тип, группу, обязательность, подсказку, видимость, доступность редактирования и список вариантов для select-полей;
- в профиле поля отображаются внутри соответствующих групп, как на предоставленном примере.

#### Минимальный состав системных групп

| Группа | Защищенные системные поля |
| --- | --- |
| `Личная информация` | Фамилия, имя, отчество, email, аватар |
| `Контакты` | Телефон, город |
| `Работа` | Организация, роль, статус, навыки, интересы, описание опыта |
| `Результаты` | Подтвержденные часы, баллы, уровень, достижения, сертификаты; значения вычисляются системой |

Системные поля могут иметь настройку видимости там, где это допустимо политикой данных, но их удаление и изменение технического кода запрещается. Результатные поля не должны редактироваться пользователем вручную.

#### Типы пользовательских полей

Первая версия конструктора должна поддерживать типы, которые уже близки к существующему `DynamicForm`:

- однострочный текст;
- многострочный текст;
- число;
- дата/дата и время;
- телефон;
- email;
- URL;
- выбор одного значения;
- выбор нескольких значений;
- флажок;
- файл/изображение, если хранение файлов безопасно включается в текущий backend.

#### Предлагаемая модель данных

Модель должна быть привязана к организации: разные организации могут требовать разные дополнительные сведения от своих волонтеров.

| Новая сущность | Назначение | Ключевые поля |
| --- | --- | --- |
| `profile_field_groups` | Группы полей организации | `id`, `organization_id`, `code`, `name`, `sort_order`, `is_system`, `is_active` |
| `profile_field_definitions` | Описание пользовательских и системных полей | `id`, `group_id`, `organization_id`, `code`, `name`, `type`, `required`, `is_system`, `is_active`, `editable_by_user`, `sort_order`, `settings` JSONB |
| `profile_field_options` | Варианты для полей выбора | `id`, `field_id`, `value`, `label`, `sort_order`, `is_active` |
| `profile_field_values` | Значения полей конкретного пользователя в организации | `organization_id`, `user_id`, `field_id`, типизированное значение или `value_json`, даты обновления |

Перед реализацией следует выбрать способ хранения значений: типизированные колонки удобнее для валидации и аналитики, `JSONB` быстрее для расширения типов. Для диплома предпочтительнее описать выбранный компромисс и ограничения поиска/отчетности.

#### API и права доступа

Необходимые группы API:

- административные CRUD endpoint для групп, полей и вариантов значений;
- endpoint получения схемы профиля для организации;
- endpoint чтения профиля пользователя с системными и дополнительными значениями;
- endpoint обновления разрешенных пользователю значений;
- endpoint загрузки аватара;
- аудит изменения схемы полей и заполненных значений.

Правила:

- системные поля нельзя удалить через API;
- администратор организации управляет только схемой своей организации;
- волонтер редактирует только собственные значения и только поля с разрешением редактирования;
- значения полей с персональными данными не доступны посторонним пользователям;
- изменения структуры и важных значений попадают в `audit_log`.

#### UI, который требуется подтвердить скриншотами в V4

- страница администратора со списком системных и пользовательских групп полей;
- раскрытая группа с активными полями и управляющими действиями;
- модальное окно создания/редактирования пользовательского поля;
- профиль пользователя с вкладками;
- вкладка `Личная информация` с системными и дополнительными полями;
- вкладка `Работа` с организацией, опытом и настраиваемыми полями;
- вкладка `Достижения и документы` с реальными результатами.

### 11.1.4 Проверка новых функций и отражение в дипломе

| Проверяемый сценарий | Подтверждение |
| --- | --- |
| Пользователь меняет аватар | скриншот до/после, URL файла и обновленный профиль |
| Администратор создает группу полей | скриншот настроек, запись БД/API и аудит |
| Администратор создает поле в группе | форма настройки, появление поля в схеме профиля |
| Волонтер заполняет дополнительное поле | профиль до/после и сохраненное значение |
| Системное поле невозможно удалить | негативный API/UI-сценарий |
| Поле скрывается после деактивации без потери сохраненного значения | состояние до/после и проверка повторной активации |
| GitHub Actions собирает проект | ссылка/лог успешного workflow и вставка результата в ВКР |

В тексте ВКР новые функции должны войти в модель данных, архитектуру API, карту экранов, макеты пользовательских форм, административные сценарии, проверку прав доступа и фактический сценарий главы 3.

## 15. Первый практический шаг к V4

Рационально начинать V4 не с переписывания текста, а с получения доказательств, которых не хватает относительно образца:

1. Снять структуру фактических таблиц, API и существующих форм/профилей из репозитория.
2. Спроектировать и реализовать миграции, API и интерфейс расширенного профиля с группами и пользовательскими полями.
3. Реализовать GitHub Actions workflow и необходимые автоматические проверки.
4. Поднять чистое демонстрационное окружение «Пульс».
5. Пройти сквозной сценарий ролей, настройки полей, заполнения профиля и формирования результатов; сохранить экраны, ответы API, аудит и результаты workflow.
6. После этого собрать DOCX V4, обновив структуру, ссылки и формальные страницы.

Так V4 станет не просто объемнее, а убедительнее: сильные стороны образца будут воспроизведены через реальные данные и реальные возможности «Пульс».
