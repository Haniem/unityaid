# Роадмапа развития UnityAid в managed single-tenant SaaS

## 1. Новое целевое направление

Для UnityAid более подходящей моделью выглядит не классический multi-tenant SaaS с общей базой данных, а **managed single-tenant SaaS**.

В этой модели каждый клиент получает отдельный изолированный комплект инфраструктуры:

- отдельный backend;
- отдельный frontend;
- отдельную PostgreSQL-базу;
- отдельный Redis, если он нужен;
- отдельное файловое хранилище;
- отдельные секреты;
- отдельные настройки домена;
- отдельные backup и restore-процессы;
- отдельные лимиты ресурсов.

То есть платформа остается SaaS с точки зрения клиента: клиент не администрирует серверы, получает обновления и поддержку. Но технически каждый клиент работает в своем изолированном окружении.

Такой подход хорошо совпадает с идеей коробочного продукта: если клиенту нужен on-prem, мы берем тот же stack и разворачиваем его на инфраструктуре клиента.

## 2. Почему эта модель лучше для UnityAid

### Сильная изоляция данных

Для организаций, которые хранят персональные данные волонтеров, учет часов, документы, сертификаты и аудит сотрудников, отдельная база на клиента выглядит убедительнее, чем общая база с `tenant_id`.

Преимущества:

- ниже риск утечки данных между клиентами;
- проще объяснить безопасность заказчику;
- проще делать backup и restore конкретного клиента;
- проще удалять данные клиента при расторжении договора;
- проще переносить клиента в on-prem;
- проще обслуживать клиентов с особыми требованиями.

### Проще путь к коробочной версии

Если каждый клиент уже живет в своем stack, коробочная поставка становится почти тем же самым:

- берем docker-compose или Helm chart;
- передаем переменные окружения;
- подключаем домен;
- запускаем миграции;
- создаем администратора клиента.

Кодовая база при этом остается общей.

### Гибкие обновления

Не все клиенты готовы обновляться одновременно. Отдельные окружения позволяют:

- обновлять клиента по расписанию;
- держать разные версии временно;
- быстро откатить конкретного клиента;
- тестировать изменения на пилотном клиенте;
- выпускать enterprise-доработки через feature flags.

## 3. Общая архитектура платформы

### Control plane

Control plane - центральная управляющая часть платформы UnityAid.

Она не хранит операционные данные волонтеров. Ее задача - управлять клиентскими окружениями.

Функции control plane:

- реестр клиентов;
- создание клиентского окружения;
- хранение тарифов и статусов оплаты;
- управление доменами;
- управление версиями приложений;
- запуск обновлений;
- мониторинг окружений;
- backup и restore;
- технический аудит;
- управление feature flags;
- панель поддержки.

### Tenant stack

Tenant stack - отдельный комплект сервисов клиента.

Минимальный stack:

- `frontend`;
- `backend`;
- `postgres`;
- `file storage`;
- `migrations/job`;
- `backup job`.

Расширенный stack:

- `redis`;
- `worker`;
- `scheduler`;
- `mail service`;
- `websocket service`;
- `object storage`;
- `monitoring sidecar`.

### Общая схема

```text
UnityAid Control Plane
  |
  |-- client-a namespace
  |     |-- frontend
  |     |-- backend
  |     |-- postgres
  |     |-- redis
  |     |-- storage
  |     |-- backup job
  |
  |-- client-b namespace
  |     |-- frontend
  |     |-- backend
  |     |-- postgres
  |     |-- storage
  |
  |-- client-c namespace
        |-- frontend
        |-- backend
        |-- postgres
        |-- redis
        |-- worker
```

## 4. Kubernetes-модель

Если разворачивать продукт в Kubernetes, для каждого клиента лучше создавать отдельный namespace.

### Namespace клиента

В namespace клиента размещаются:

- Deployment backend;
- Deployment frontend или ingress на статическую сборку;
- StatefulSet или managed PostgreSQL instance;
- Redis, если нужен;
- Secret с переменными окружения;
- ConfigMap с настройками клиента;
- PersistentVolumeClaim для файлов, если не используется S3;
- CronJob для backup;
- Job для миграций;
- Ingress для домена клиента;
- NetworkPolicy;
- ResourceQuota;
- LimitRange.

### Пример именования

```text
unityaid-system
unityaid-client-dobrye-ruki
unityaid-client-university-demo
unityaid-client-corporate-help
```

### Изоляция

Для каждого namespace:

- отдельные секреты;
- отдельная сеть;
- отдельные лимиты CPU/RAM;
- отдельная БД;
- отдельные backups;
- отдельный ingress host;
- отдельные логи с меткой клиента.

## 5. Docker Compose для on-prem и малого SaaS

На раннем этапе можно не начинать с Kubernetes. Для первых клиентов достаточно генерировать отдельный docker-compose stack.

Пример:

```text
client-a/
  docker-compose.yml
  .env
  data/postgres
  data/uploads
  backups

client-b/
  docker-compose.yml
  .env
  data/postgres
  data/uploads
  backups
```

Плюсы:

- быстрее стартовать;
- проще внедрять у одного клиента;
- проще показывать коробочную поставку;
- меньше DevOps-сложности.

Минусы:

- сложнее массово обновлять;
- сложнее мониторить десятки клиентов;
- больше ручной работы;
- хуже масштабирование.

Рекомендуемый путь: сначала автоматизированный compose-stack, затем Kubernetes/Helm.

## 6. Что меняется в модели данных

В managed single-tenant модели не нужно добавлять `tenant_id` во все бизнес-таблицы как обязательную основу изоляции, потому что каждый клиент имеет отдельную базу.

Но все равно нужны глобальные сущности в control plane:

- `clients`;
- `client_environments`;
- `client_domains`;
- `client_versions`;
- `client_subscriptions`;
- `client_feature_flags`;
- `client_backups`;
- `client_deployments`;
- `client_health_checks`;
- `client_maintenance_windows`.

Внутри клиентской базы остаются текущие бизнес-сущности:

- users;
- organizations;
- organization_members;
- events;
- tasks;
- time_entries;
- news;
- knowledge_articles;
- notifications;
- gamification;
- analytics;
- certificates;
- audit_log.

### Важная оговорка

`organizations` внутри клиентской базы остаются. Они больше не означают SaaS-клиента, а означают подразделения, филиалы, направления или команды внутри клиента.

Например:

- tenant stack клиента "Добрые руки";
- внутри него организации "Магнитогорск", "Челябинск", "Экологическое направление", "Помощь пожилым".

## 7. Роли в новой модели

### Platform admin

Администратор платформы UnityAid.

Работает в control plane.

Может:

- создавать клиентов;
- запускать окружения;
- обновлять версии;
- смотреть healthcheck;
- управлять тарифами;
- включать модули;
- смотреть технические логи;
- запускать backup/restore.

### Support engineer

Сотрудник поддержки платформы.

Может:

- видеть список клиентов;
- смотреть техническое состояние;
- подключаться к клиентскому окружению по регламенту;
- запускать диагностику;
- не должен иметь прямой доступ к персональным данным без отдельного разрешения.

### Client owner

Главный администратор клиента внутри его stack.

Может:

- управлять организациями;
- управлять пользователями;
- назначать роли;
- видеть отчеты;
- настраивать брендирование;
- управлять сертификатами и документами.

### Organization admin, coordinator, volunteer

Остаются как в текущей системе.

Они работают только внутри клиентского окружения.

## 26. Основные риски

### Стоимость инфраструктуры

Отдельный stack на клиента дороже общей multi-tenant базы. Нужно компенсировать это тарифами и возможностью отключать лишние компоненты для маленьких клиентов.

### Сложность эксплуатации

Чем больше клиентов, тем важнее автоматизация deploy, backup, мониторинга и обновлений.

### Разные версии у клиентов

Гибкость обновлений полезна, но нельзя допустить хаос версий. Нужны release channels и срок поддержки старых версий.

### Перенос данных

Нужно заранее проектировать экспорт и restore, чтобы клиент не был заперт в системе.

### Безопасность доступа поддержки

Если команда UnityAid имеет технический доступ к клиентским окружениям, все такие действия должны логироваться и регулироваться.

## 27. Итоговая стратегия

Новая стратегия UnityAid:

1. **Не строить общую базу на всех клиентов.**
2. **Создавать отдельный stack для каждого клиента.**
3. **Управлять stack через control plane.**
4. **Начать с автоматизированного docker-compose.**
5. **Перейти к Kubernetes namespace/Helm по мере роста.**
6. **Сохранить on-prem как естественный вариант поставки.**

Такой путь дает более надежную изоляцию, проще продается организациям, лучше подходит для персональных данных и делает коробочную версию продолжением SaaS-архитектуры, а не отдельным продуктом.
